❯ What is a world model exactly?                                                

● Skill(anthropic-skills:learn)
  ⎿  Successfully loaded skill

● A world model is a learned model of how some environment behaves. You give it
  the current state and an action, and it predicts what happens next. That lets
  an AI system try out the consequences of an action in its head before doing
  anything for real.

  You already have one. You know a glass will shatter if you drop it, and you
  don't need to drop it to find out.

  How it differs from an LLM
  - An LLM predicts the next word of text.
  - A world model predicts the next state of a system: physics, a game, a
    network, a spacecraft.

  What "JEPA-style" adds (JEPA is Yann LeCun's Joint-Embedding Predictive
  Architecture)

  A naive world model tries to predict every detail of the future, such as every
  pixel or every telemetry value. Much of that is noise nobody could predict.
  JEPA instead predicts a compressed summary (an embedding) of the future state.
  It learns the parts that matter and ignores the rest.

  The two things a world model is used for

  state + action ──► world model ──► predicted next state
                                           │
                     actual next state ────┴──► compare
                                                 │
                          small gap = "as expected"   big gap = SURPRISE

  1. Planning: try several actions in simulation and pick the best one.
  2. Watching: compare what it predicted with what actually happened. A big gap
     between the two ("surprise") is the alarm.

  Periapt uses it mainly for the second job. It learns what normal behaviour
  looks like around a patch. When the emulator run, the canary spacecraft or the
  live rollout drifts away from that prediction, it raises a flag for a human.

  A weak spot to prepare for the viva: a world model is only as good as the data
  it learned from. Spacecraft telemetry is limited, and each mission is
  somewhat different, so expect someone to ask "trained on what?"

  A question to check your understanding: a patch goes up to a canary satellite.
  Name one thing the world model would expect to see afterwards, and one
  observation that should make it raise a flag. Having your own answer to that
  is worth more in the viva than any definition.

❯ so it's an uh, alternative to physics and simulation?                         

● Partly. A better way to say it: a world model is a simulator that was learned 
  from data instead of written from equations. It's often used alongside physics
  simulation rather than as a replacement.

  ┌─────────┬───────────────────────┬──────────────────────────────────────┐

  │ Strong  │ The physics is well   │ Nobody has written equations for it: │

  │         │                       │ how subsystems interact              │
  ├─────────┼───────────────────────┼──────────────────────────────────────┤
  │ Weak    │ Anything the          │ Situations it never saw in its data. │
  │ where   │ equations leave out   │  It can be confidently wrong there.  │
  ├─────────┼───────────────────────┼──────────────────────────────────────┤
  │ Cost    │ Can be slow and       │ Fast once trained                    │
  │         │ expensive to run      │                                      │
  └─────────┴───────────────────────┴──────────────────────────────────────┘

  In practice they're often combined. You train the world model on simulator
  output plus real data, or you let physics handle what it knows and the learned
  model cover the rest.

  In Periapt, the two sit side by side. The flight-software emulator is the
  simulation: it actually runs the patched code. The world model's job is to
  judge that run. It predicts what normal behaviour should look like and flags
  where the emulator run, and later the canary satellite, drifts away from that
  prediction. The emulator shows what happened, and the world model says whether
  that looks right.

  A question to test this: why not just have engineers write fixed rules like
  "flag if battery temp exceeds X"? What would a world model catch that fixed
  rules miss?

● Not useless, but you've found a real gap. In Periapt the emulator produces
  telemetry, not a verdict, so something has to decide whether a run looks
  healthy. The real question is whether that judge needs to be a learned world
  model. Your own notes already moved this way: after review R6 and Q26 the
  world model stopped predicting what new code does and became "compare against
  normal behaviour." That job has cheaper alternatives:

  Alternative: 1. Limit checks (red/yellow thresholds)
  How it judges: "Battery temp > X → alarm"
  Catches: Obvious breaches. This is the standard tool in spacecraft ops, easy
  to
  explain and certify.
  Misses: Values that are each within limits but wrong together, and slow drift
  ────────────────────────────────────────
  Alternative: 2. Differential run
  How it judges: Run the emulator with and without the patch on the same inputs
  and diff the telemetry
  Catches: Anything the patch changed, with no ML at all. Very strong at the
  emulator stage.
  Misses: The canary stage: you can't run patched and unpatched on the same
  satellite at once. Also, a difference isn't always bad, because the patch is
  meant to change things.
  ────────────────────────────────────────
  Alternative: 3. Statistical tests
  How it judges: Compare the run with historical distributions (z-scores,
  change-point detection)
  Catches: Shifts in single channels
  Misses: Relationships across many channels
  ────────────────────────────────────────
  Alternative: 4. Learned forecaster
  How it judges: Predict the next telemetry and flag big errors. JPL published
  an
  LSTM detector like this for its spacecraft (from memory, not in your research
   file yet).
  Catches: Cross-channel patterns and subtle drift
  Misses: Needs training data and is harder to explain
  ────────────────────────────────────────
  Alternative: 5. JEPA-style world model
  How it judges: Same idea as 4, but it predicts in embedding space,
  self-supervised across the whole fleet
  Catches: Same as 4, with less sensitivity to noise
  Misses: Same as 4, plus more complexity. Item 7 already shows its data is thin

  compared with typical JEPA training.

  The honest takeaway is that 4 and 5 do the same job. After the R6 reframe,
  Periapt's "world model" is in practice a learned anomaly detector wearing a
  fancier name. Your Research Findings item 7 cites ESA-ADB, a benchmark built
  to compare exactly these detectors, so it could settle whether JEPA beats a
  plain forecaster. Your file doesn't record that result yet.

  My recommendation: a layered design. Use limits plus the differential run as
  the first line, because they're cheap, explainable and what engineers already
  trust. Keep a learned model as the fleet-wide safety net for the cross-channel
  drift that rules can't name. Whether to still call it JEPA comes down to
  this: it earns creativity marks, but it's the claim a viva is most likely to
  attack.

  That changes a locked architecture decision, so it's your call. I haven't
  edited anything. Which way are you leaning: keep JEPA and defend it, or
  downgrade to "learned anomaly detector" and put the differential run up front?

  The flaws, and how to counter each

  1. The patch is supposed to change things. A diff will light up on intended
     changes too.
     → Every patch ships with an expected-change manifest written by the
     flight-software team: "channels X and Y should change, by roughly this
     much." The diff only alarms on changes that weren't declared. This also
     makes the agent's job more concrete.
  2. The canary has no control group. You can't run patched and unpatched on the
     same satellite at once.
     → Compare it with sister satellites on the same bus and orbit, and with its
     own pre-patch baseline at the same orbital phase (eclipse vs sunlight).
     This is my reasoning, not something in your sources.
  3. The emulator is not the real satellite. It won't reproduce an aged battery
     or a degraded sensor.
     → That's exactly what the canary is for. Your spec's T5 already pairs this
     with an A/B partition, a watchdog and a least-critical canary. Say
     explicitly that layers run at both stages.
  4. Slow failures outlast the canary window. A memory leak might take weeks to
     show.
     → Add a soak period before each wave, and keep the learned model watching
     after rollout ends. That long, fleet-wide watch is where it earns its place
     over rules.
  5. Alarm fatigue. Three layers means more alarms, and operators start ignoring
     them.
     → Give the layers different authority. A limit breach halts the rollout. An
     undeclared diff holds it for a human. A learned-model alert alone raises a
     flag and never rolls back. Any layer can stop things, and only a human can
     clear a stop. That rule also gives your Governance section a clean line.
  6. No proof the learned layer beats a simple forecaster.
     → Name the test: benchmark it against a plain forecaster on ESA-ADB (844
     annotated events, already in item 7) and report false-alarm rate. Present
     it as roadmap, not as a result, because you haven't run it.
  7. Adversarial blind spot. If an attacker controls the ground segment, they
     can forge normal-looking telemetry or sign a malicious patch. Every layer
     then judges faked data.
     → Be upfront that this is outside the judge's scope. It's handled by patch
     signing, telemetry integrity checks, and the spec's rule that anything
     touching command authentication is human-only.
  8. Moat side effect. Layers 1–3 are commodity tools, so the judge is no longer
     a differentiator.
     → That's fine, and it matches Q26's conclusion: the moat is the flaw-to-fix
     flow plus cross-fleet data, and the judge is a safety net. Frame the
     layering as defence in depth, a real security principle, which also helps
     storytelling.

  What remains open: flaw 6 is unproven until someone runs the benchmark, and
  flaw 7 is out of scope by design. Both are defensible if you name them
  yourself before a grader does.
